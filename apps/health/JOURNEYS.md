# ALOHA Health · 第一批用户旅程与交互契约（UX Prototype）

> **决策：以用户目的为入口，而非七张模型管理表。** 当前原型只有虚构数据，所有操作仅在本次浏览器页面内存中生效。该文件约束交互，不修改 LifeSpace Health Schema。

## 先回答用户的六个问题

| 编号 / 旅程 | 用户问题 / 触发场景 | 起点 → 决策 → 操作 → 完成反馈 |
| --- | --- | --- |
| J1 快速记录 | “刚测过一次，想记下来” | **首页「快速记录」/ 时间线「新增记录」** → 选择测量/事件/评估 → 只填写对应必填项、可关联健康问题/资料 → 保存 → **刚创建的记录详情** → 返回起点 |
| J2 持续关注 | “一个健康问题最近怎么样？” | **身体·关注 → 人体图选点或直接搜索全部关注事项 → 进入同一 Concern 详情**；也可从首页关注事项直达详情 → 从对应区块添加测量/事件/方案/资料/评估 → **返回原关注事项** |
| J3 指标趋势 | “血压最近有什么变化？” | 身体·指标 → 选择数值指标 → **切换「日／月／年」时间粒度** → 查看实际观测点、周期均值与记录数，缺失周期只用平滑曲线连接、不填造记录 → 点击单次记录点追溯原始来源，或「记录一次」（预填指标和单位） → 保存 → 新记录详情 → **返回当前指标详情** |
| J4 整理资料 | “拿到报告，放哪里？” | 身体·资料 / Concern 依据区 → 添加资料 → 选择本地文件名（无读取、无上传） → 虚构提取预览 → 用户明确勾选是否添加模拟测量 → 确认 → **资料详情** → 查看关联模拟观测与原健康问题 → 返回原页面 |
| J5 干预与方案 | “这段时间有什么计划？” | 健康问题 / 身体·干预 → 新建方案 → 填写内容、周期和日期 → 保存 → 方案详情 → 首页演示完成状态 / 回顾相关问题。实际 Task 与 Recurrence 尚未接入 |
| J6 按时间回顾 | “几周前发生了什么？” | 身体·时间线 → **按月、日排列的纵向时间轴**（左侧日期、连接线和节点，右侧测量／健康事件／评估卡片）→ 关键词搜索及「全部／测量／事件／评估」筛选 → 点击进入原记录详情并追溯来源、所属关注和依据 → **返回原时间轴的浏览位置与筛选状态** |


## 指标详情信息减法与阅读顺序（2026-10-28）

- **第一眼：** 最新实际数值和明确记录日期（例：67.2 kg｜最新记录 · 2026.10.20）。历史点不能被默认当作第二个最新结果。
- **第二步：** 「变化趋势」标题不再额外重复单位；「日／月／年」旁也不放单位。单位只出现在实际数值上下文中（最新值、主动选中的点、历史记录）。
- **第三步：** 图表默认没有选中节点，因此下方不显示任何另一条观测值；用户明确点击／键盘选中一个真实节点后，才显示简洁的「已选 · 日期 · 当日观测／当月平均／当年平均、数值、记录数量」，单次观测可直接查看原记录，也可取消选择。切换粒度清空旧选择。
- **历史记录：** 所有实际记录按日期倒序，点击进入原记录。列表卡片不与趋势卡片等高拉出空白；宽 Desktop 趋势区稍宽，Mobile / AI 侧栏窄时上下排列。
- **事实边界：** 不改变 HealthMetric/HealthObservation，也不在空白日期补造事实；沿用原先的周期平均与平滑连线。

## 指标列表状态筛选与动态生长参考（2026-10-28）

- **指标列表旅程**：顶部保留关键词搜索；下方增加「全部／范围内／超出范围／未判定」轻量筛选及结果数量。状态只依据该指标**最近一条有效、可比较的测量**与适用参考范围得出；没有最新数据、未设置范围、数值或单位不可比较、非数值指标均归「未判定」。不会把无从判断的指标算作「正常」。筛选和搜索可同时使用，空结果需有清晰提示。显示指标行时只对越界值保留方向箭头。
- **年龄变化参考的待实现方案**：固定数值范围不适合儿童身高、儿童 BMI 等**随年龄和适用人群变化的参考指标**。为指标设计第二类参考策略「生长曲线／动态标准」，应引用**明确来源、版本、单位和适用年龄范围**的参考数据集，而不是一张写死在用户 Metric 中的上下限表。每次评估以 Observation.observedDate 结合受测者出生日期计算**观测当时的月龄**，再选参考标准适用分组；需要按标准规定获取性别等参考条件，缺少时返回「未判定」，绝不由姓名推断。
- **生长指标展示**：真实身高点与随月龄变化的参考分位数曲线并排展示，标注其标准、分位数以及纵向生长趋势；不同百分位不是按成绩排名，“高于标准”不自动等于身体异常。趋势变化与生长速度需与单点所处分位数区分。
- **实现边界**：本轮仅实现固定范围的列表筛选；动态标准**只更新设计与接口约束，不在 ALOHA 原型硬编码儿童身高阈值或伪造动态区间数据**。选择和校验 WHO/CDC/适用地区标准的数据集及版本、授权/归因、引用方式和 LifeSpace 适配后再单独实施；不新增 LifeSpace 基线模型。

## 范围提示视觉约定：越界用方向箭头、趋势用淡虚线（2026-10-28）

- 在指标列表、最新结果、历史观测和观测详情，只有值低于下限或高于上限时，显示小型 ArrowDown / ArrowUp，不再逐行显示“低于/高于/在参考范围内”文案。范围内、未设置范围、无法比较：不绘制“正常”图标；箭头悬停和辅助阅读保留“低于参考范围/高于参考范围”，**不是环比升降趋势**。原报告的 interpretation 是证据文字，仍在详情独立显示。
- 设置参考上下限时，趋势图在数值坐标上画低对比度的淡色水平虚线（单端就画一条，重合就一条），标识“上限/下限 + 数值”；真实观测曲线前置，不采用大块健康背景颜色。纵轴域容纳范围值以确保刻度真实，不将参考值混入观测周期聚合。
- 独立来源、单位校验、参考范围覆盖逻辑不变。该调整只影响虚构 PWA 原型，LifeSpace 权威 Schema 草案不增加字段。

## 指标参考范围：范围比较不是医学诊断（2026-10-28）

- **用户旅程**：创建数值指标时可选填默认参考下限、上限、来源；录入观测时如果本次报告附带不同的范围，可覆盖当次上下限及来源。没有来源的手动范围必须标注“来源未注明”，不能宣称通用正常标准。个人体重目标属于 Goal，不默认写成 HealthMetric 的医学参考范围。
- **比较顺序**：Observation 有任一当次边界时只采用**本次完整范围**（不能把本次上限与指标默认下限拼成不存在的范围）；否则采用指标默认范围。先核对单位，无可靠转换时拒绝比较；无效或非数值记录不比较。计算输出只能是“低于参考范围／在参考范围内／高于参考范围”或“暂无法比较”，**不等于诊断**。原报告的 `interpretation` 由来源独立保存，绝不被范围比较自动覆盖。
- **指标详情**：最新值旁显示淡色小状态点及文字，趋势下方可有低透明“指标默认参考范围”背景带（仅画可见部分），历史记录列出各次比较。进入观测详情可看当次范围、来源与原报告标记，二者可能不同，必须并列而不混淆。
- **Schema 所有权**：权威草案在 ALOHA Health Notion 的 HealthMetric/HealthObservation 章节及两个 JSON Model Definition。每个模型增加可选的 `referenceLow:number`、`referenceHigh:number`、`referenceSource:string`；应用演示会校验 lower ≤ upper，正式依赖 LifeSpace Console Validate 与服务端领域规则。原型不发布 LifeSpace、不上传真实健康资料。

## 「指标 → 观测趋势」按日、月、年查看（2026-10-28）

- **用户目的**：从同一个健康指标的历史观测看不同时间尺度的变化。图表页内选择「日／月／年」，不是三个独立路由或三种记录模型。时间维度状态只影响显示，不修改任何 HealthObservation。
- **周期取值约定**：日模式按自然日归类（月/年按自然月与公历年），每个周期内有效的数值观测取**算术平均值**，明确显示「该周期 N 次真实观测」；当周期只有一条有效记录时展示原值并提供「查看记录」进入原记录详情。属于展示聚合而不是重新生成一条健康记录或诊断判断。
- **无观测周期**：按真实日期/月份/年份成比例分配横轴位置，在相邻实际有记录的周期之间用**不会超出端点值范围的平滑贝塞尔曲线**连接。中间没有观测的日期不生成点、数值、虚构记录或医学推断；不会把连线上任意一处当作真实测量。单点只显示点，不凭空延伸趋势或增加未来数值。
- **数据与导航边界**：只绘制 HealthObservation 中可用、有限的数字值，排除明确标记的无效记录和不合法日期。文字型和是/否型指标不伪装成折线图；历史记录列表仍保留所有原记录及其状态。切换粒度与查看聚合值不会重写原始数据。
- **视觉**：一个 Health Token 主题色的细线、小点和轻量刻度，右下方显示当前周期均值/观测次数。Mobile/Tablet/Desktop 均可用，AI 侧栏不会中断详情，继续保留 Lucide 和标准 Header/按钮样式。该功能仍是公开仓库中的虚构浏览器原型，无真实数据来源或 LifeSpace Schema 变更。

## 「时间线」展示与用户旅程（2026-10-28）

- **定位**：「时间线」是 HealthObservation、HealthEvent、HealthAssessment 三种已发生事实的**只读时间投影**，不是第四种记录模型。没有明确发生日期的资料/干预方案不应被偷偷当成时间事实塞入轴线；HealthDocument 的发行日期不能冒充独立事件。
- **布局**：按月份分组（倒序），同月再按具体日期分组；日期只显示一次，纵向细线串联各条记录。左侧日期 + 星期，右侧轻量记录卡：类别、真实标题／数值，点击回原来的测量/事件/评估详情。跨月/同日的相对顺序稳定，不能编造时分秒。
- **搜索与筛选**：沿用页面唯一的搜索框，时间轴内部仅新增「全部、测量、事件、评估」四个轻量筛选，不复制「新增记录」操作。新增入口仍由页头的统一菜单提供；新建、修改或删除后时间轴由既有记录自动更新。无结果和指定类型下无记录都应有明确提示。
- **返回上下文**：由时间轴进入详情后，返回保持原类型筛选、关键词和浏览滚动位置，不重新跳到第一条。原来的跨记录详情路由栈继续使用。
- **Mobile/Desktop/Agent**：共用纵向轴视图、移动端缩窄左侧日期栏、内容宽度自动伸缩；AI 侧栏存在时只压缩内容区，不开第二个时间线，也不影响会话。使用 Lucide 与现有 Health Token，避免大色块和渐进式无限滚动的过度设计。
- **数据限制**：仍是虚构且仅保存在本次页面内存里的模拟健康记录；不创建新的 LifeSpace Domain Model 或真实查询/API。

## 交互动作唯一性 / One Primary Action per Screen

| 当前页面 | 顶部唯一的新增动作 | 附近允许的次级操作 |
| --- | --- | --- |
| 首页 | **快速记录** → 测量 / 事件 / 评估三选一 | 查看关注事项、指标、全部资料；不在同一页额外复制快捷新增按钮 |
| 身体·关注 | **添加关注** | 人体图与完整可搜索列表同页；正面、背面、未定位及已结束事项均可找到，点位置会选中右侧该项 |
| 身体·指标 | **新增指标**（定义指标类型） | 进入指标详情后才出现「记录一次」 |
| 身体·时间线 | **新增记录** → 测量 / 事件 / 评估 | 搜索记录；不再有“记一件事”和并列的三种快捷新增 |
| 身体·资料 | **添加资料** → 导入与核对 | 搜索已保存的资料 |
| 身体·干预 | **新建方案** | 搜索方案 |
| 具体记录详情 | **修改**（不是第二个全局新增） | 删除；关联卡片有各自明确的「添加测量 / 添加事件 / 添加资料 / 添加方案」等 |

| 健康问题详情 | 不再有含糊的“新增记录”总按钮 | 对应卡片直接新增对应对象，自动关联当前健康问题 |

**规则：** 顶部 Contextual Action 由当前 Tab 决定。下方搜索区**只负责筛选**，不再复制创建入口。不同目标的卡片内按钮可以保留，但必须具备明确的对象和上下文；UI 元素数量不是目标，避免重复和意外跳转才是目标。

## 首页与「关注」工作区的边界（2026-10-28）

- **ALOHA Health 首页**以时间与行动为中心：近期变化、任务、指标和快速记录。
- **身体 → 关注**将人体二维定位与全部 HealthConcern 列表合并在同一工作区：正面/背面两种视图，每个 **HealthConcern 关联独立一个定位点**，不再创建或显示 BodyMapRegion 部位分组。用户点某个点 → 右侧完整列表高亮对应关注事项 → 进入详情；也可以直接从右侧搜索并进入。点上没有“胸部/上肢”区域与数字聚合。
- **正背面发现性 / 并排试验**：初始显示正面；人体图卡片宽度不足时固定显示「正面 N」「背面 M」切换，确保用户不切面也知道另一面有关注。**图卡自身可用宽度至少约 30rem（480px）时**同时展示正背面；两个 11.5rem（约 184px）图像与 0.75rem（约 12px）间距固定后整体居中，避免网格等分列把图推得过远。该断点来自两张图尺寸、间距和留白的计算，不是对全部 Desktop 的硬编码规则；不影响右侧关注列表。当 AI 打开导致内容缩窄，自动回退单图切换。每个点只关联本面对应的 Concern。
- **正背素材**：正面继续使用用户提供的 `body-front-outline.svg` 原始 clean 轮廓；背面使用独立的 `body-back-outline.svg`，保持轮廓、裁剪区域和 244:475 宽高比一致，只加入少量轻描的后背识别线。前后分别使用 `BODY_MAP_ASSET_IDS.front/back` 的独立版本 ID；坐标按各自素材解释，不在切面后悄悄沿用不兼容版本。
- **一个问题一个点**是 MVP 的最简规则；多个问题落在同一位置时数据仍然独立，右侧各有一行，但图上的点可能重叠。未来如真实用户需要一项 Concern 多处定位，再评估 1:N 的 BodyMapBinding，不提前扩展 LifeSpace HealthConcern Schema。
- **手动定位**：从右侧已标记或未标记的问题点击定位图标 → 选择正面/背面 → 点击轮廓内具体位置 → 预览点 → 确认写入浏览器演示状态。取消不改变原定位，不从名称推断部位。
- **网格层次**：极淡 36px 网格只作为图像背景，增加覆盖轮廓内部的独立不透明填充层，保证**人体内部没有网格**；用户提供的原始线条 SVG 仍按 244:475 等比渲染且不修改。此图形仍需 Preview 实际视觉评估。
- **信息减法**：图上不需要「身体图」标题；右侧只保留一个「关注事项」列表和搜索，不按当前正背面另建重复列表。每条 Concern 只展示一次，简短标注正面／背面／未定位以及状态。窄内容宽度（含打开 Agent）图上卡下，点击点后滚动到列表。
- **ALOHA 公共入口**：Mobile 第五 Tab 名为「更多」，与其他 Tab 一样是完整页面，不是弹出菜单；共享一个 `AlohaHub` 内容组件可在更多页内部显示应用导航、账号、安全、授权、通用设置和帮助。Desktop 顶部 ALOHA 入口也导航到相同的更多页；Desktop 左侧导航不再额外复制一个“更多”行。切页不重置 Agent 对话。
- **平台边界**：`BodyMapBinding` 属于 ALOHA 展示投影，具有 `concernId,view,assetId,point{x,y}`；不属于 LifeSpace HealthConcern 规范属性，所有样例纯虚构且刷新即重置。

**合并说明：** 旧「概览」和「健康问题」两个 Tab 已整合为唯一「关注」。身体二级导航现在是「关注／指标／时间线／资料／干预」。新增主操作为「添加关注」，首页所有「查看全部／关注事项」入口统一进入「关注」。正在编辑或查看详情时返回仍回原关注视图，选中人体的正背面与关注位置在页面切换后保留。


- **列表选中视觉**：取消选中 Concern 行左侧的绿色竖线，统一使用极淡的无方向性底色与约 1px 的低对比轮廓，同时继续通过关联点光晕和少量文字强调表示当前选择；不对整张卡片做大块染色。

**关注度已作为原型体验项：** 手动选择「未设置／日常关注／重点关注／优先处理」，仅代表用户自行安排的跟进优先级，**不是医学严重程度**。用灰、绿、琥珀、柔和珊瑚色的约 10px 点及浅光晕表现；选中点有约 3 秒轻柔呼吸，系统减少动态效果时关闭动画；标签保留文字，不仅靠颜色。关注度只存 ALOHA 演示应用状态，不成为 LifeSpace HealthConcern 字段。

**仍不做：** 自动医学分类、真实数据持久化、一个 Concern 多定位、同点位碰撞自动解算。关注位置与颜色均不代表风险或诊断。

## 保存、返回、取消与来源

- **保存后**：显示刚创建的对象的详情，能立即核对内容和关联，而不是一律跳回时间线。
- **返回**：使用本次浏览的原始位置。首页 → 关注事项 → 相关观测时，返回应先回到关注事项，再回首页。指标详情 → 测量也是同样规则。
- **编辑原记录**：保存后留在同一记录详情，不产生多余历史记录。
- **取消**：关闭表单，原页面、滚动内容和已展开的 AI 对话不被重置。
- **失败**：表单保留已填写的信息，直接给出缺项或日期规则；允许修正后再次提交。
- **数据关联**：HealthConcern / 证据来源是显式选择，不能因为访问过某页面就自动把不相关记录绑定过去。只有在某个健康问题的「添加」入口中才预填该关联。
- **删除**：原型解除关联而不级联删除健康事实；已有观测的指标禁止删除或改值类型。

## 七个领域模型与用户任务的边界

- **HealthConcern**：纵向专题，容纳关联关系，不拥有/复制原始健康事实。
- **HealthMetric**：指标定义，创建一次、可持续复用。
- **HealthObservation**：一次按类型（数字/文本/是-否）录入的原始结果；来源可以是手工或报告。
- **HealthEvent**：发生过什么，时间轴上的事实。
- **HealthDocument**：保留原报告的证据入口；演示只保存文件名。
- **HealthAssessment**：有日期和依据的判断/评估，独立于原始结果。
- **HealthRegimen**：持续方案；执行任务由后续平台机制处理，不在 Health 浏览器内自建定时服务。

## 2026-10-30 · HealthConcern 真实 Semantic Relation 接入（Staging 候选）

> 本节针对 Live 模式（`VITE_HEALTH_DATA_MODE=live`）；以上 UX Prototype 的演示态说明不代表真实服务状态。本功能仅在 ALOHA Health Preview 分支候选，必须通过实际 Staging 验收后才能声明已发布。

- **所有权**：HealthConcern / HealthMetric / HealthObservation / HealthEvent / HealthDocument / HealthAssessment / HealthRegimen 仍是 LifeSpace Core 普通模型；关系使用 Core 原生、同一 Space 内的有向 Semantic Relation，**不向模型添加 `concernIds`**，也不把关系存进 Health 的 Durable Object。
- **方向与谓词**：从当前用户拥有的 `health_concern` 作为 source 指向目标记录，指标采用 `monitors`，其他五类目标采用 `relates_to`。此语义为“正在关注/相关”，绝不隐含医学因果。原有 `health_assessment --based_on--> health_observation/document` 是另外的证据关系，不由本期的 Concern UI 代替。
- **读取**：仅进入 Concern 详情时拉取该 Concern 的有向关系；按当前 Core 成员关系验证主体，并由 Core 验证两个端点的可读权限。前端按关系中的目标 Model/Record ID 显示相关指标、测量、事件、资料、评估、方案；切换 Space / Concern 时清空旧关系，防止跨主体混用。
- **创建关联**：在 Concern 详情通过「关联现有记录」选择目标类型和现有记录。进入当前 Concern 的各类「添加」入口时自动预选当前 Concern；先持久化原始事实，再调用关系创建。若事实成功、关联失败，**必须分别提示**，不可误报为整体成功。LifeSpace 对重复关系创建有幂等约束。
- **解除关联**：只 DELETE 关系 ID；不修改/删除任何源或目标原始记录，Core 对关系执行独立授权。删除 Concern 时由 Core 的模型删除生命周期处理已存在的关系，Health 自己仅清理应用展示投影。
- **安全**：浏览器不提交 source、predicate、其他用户 ID 或 Core 地址。BFF 从当前 Access Session、LifeSpace 当前 Space Person 解析拥有者，对目标记录执行 Model/Person 校验（Metric 是 Space 共享指标目录）；Core 再核验双方的 Application/Model/Grant/Policy 权限。只有指定 Concern 的关系可解除；没有授权不得从 BFF 查询、写入或删除其他人的关系。
- **范围限制**：暂不做全应用语义关系编辑器、批量关联、关系传播、AI 自动关联，或关联不同 Space 的健康事实；普通记录详情上的关系多选与 Assessment 证据 `based_on` 留待下一项。实际多人、跨 Space 授权仍由 LifeSpace 授权契约单独处理。

## 2026-10-30 · HealthConcern 详情密度和关联编辑 UX V2

- **四张用途卡片**：保留「现在怎么样？」「正在做什么？」「最近发生了什么？」「有哪些依据？」四个区块；不再将低频关联操作放入独立大卡片。每张业务卡片提供弱强调的「管理关联」，只有进入管理状态时才露出「关联已有记录」选择器和逐行解除按钮；普通浏览的行只负责进入详情。
- **现在怎么样？层次**：状态和摘要先读；关注度与起止日期用一行/自动换行的紧凑元数据，不再撑开大段空白；「追踪指标」（Metric, 看趋势）和「近期测量」（Observation, 看单次事实）明确分区，避免把指标定义与观测值混在同一层次。
- **排序与分页**：相关测量按 observedDate、事件按发生日期、方案按 startDate、资料与评估混合按 issuedDate/assessedDate 倒序。相关指标按其最近观测日期排序。每个子列表独立展示 3 条/页，只有超过一页才出现上一页/下一页，页面切换或换关注事项时回到第一页。当前属于**客户端展示分页**，不是 LifeSpace Core cursor API；后续真实数据量达到加载瓶颈时另行补服务端分页，不能假装已无限加载。
- **关联边安全**：展示层解关联仍只调用 LifeSpace Semantic Relation DELETE；必须明确点击「管理关联 → 对应记录的解除按钮 → 原生确认弹窗」。取消不产生请求，确认也不删除指标、观测或资料本体。
- **测量录入**：指标选择器支持搜索名称（宽窄字符规范化与不区分大小写），历史观测按时间倒序去重得出最近使用的最多五个指标。可以在测量表单直接快速创建 Metric（名称、数值/文本/是非、可选单位）；成功后自动选择，不清空日期、参考资料、关联的 Concern；失败保持已填写草稿，不把当前 Observation 误保存。完整指标默认参考范围仍可进入指标详情后编辑。
- **Toast 位置和时长**：采用底部居中 Snackbar，Mobile 抬高避开固定底部导航，Desktop 避开常见右下角动作按钮；成功反馈自动约 4.2 秒消失，错误约 7.5 秒，均保留主动关闭。表单中的必填/关联操作失败继续以就近 inline error 呈现，不将需要重试的关键信息仅寄托给消失的 Toast。此位置符合 Material Design Snackbar 的底部提示与不遮挡主要操作的原则。
- **范围**：只调整 ALOHA Health UX 和前端展示，不新增 LifeSpace Model/迁移、健康诊断语义、AI 或性能策略。继续保持 Draft PR/Staging 验收流程。

## 2026-10-30 · Architecture correction: Settings is a peer /settings route

The earlier proposal `/health/hub/settings` / `/assistant/hub/settings`
was rejected: a shared ALOHA preference UI must not be owned by Health's
PWA path. Canonical public route is **`aloha.aisr.online/settings`**
(redirected to `/settings/`). Health and Assistant Hub link to it; neither
renders or deploys its own copy of the settings page. A new minimal
`apps/settings` service provides a shared Settings UI plus authenticated
Identity User profile and Core authorized Spaces, with an independent Worker
and manual staging workflow. Account editing remains `account.aisr.online`.

Default space is the per-origin `aloha.space` browser preference; it does
not grant permissions and it cannot be synchronized between distinct
`workers.dev` staging hosts. The Health client migrates its previous
`aloha.health.space` key only when it can independently verify membership
against Core. Production stays unchanged until route activation is approved.
